# 编写与扩充 PRD

## 何时使用本技能

- 仅有原型、交互稿、改动点列表，需要落成可评审的 PRD。
- 已有简略 PRD（几段话、大纲、口头纪要），需要扩充为完整 PRD。
- 用户明确提到「PRD」「需求文档」「产品说明」「从原型写需求」。

## 项目约定（必须遵守）

### 1. PRD 写作规范（技能内置）

在动笔编写或扩充正文之前，必须完整读取与本技能 `SKILL.md` 同级的 **`references/prd-guide.md`**，并严格遵循其中的格式、章节、术语与约束。不要求仓库内存在 `ref/prd-guide.md` 或其它同名文件。**PRD 的章节结构、标题层级与正文组织一律以该指南为准**；若与本 `SKILL.md` 正文其它段落冲突，**以 `references/prd-guide.md` 为准**。

更新写作规范时，**只编辑**技能包内的 **`references/prd-guide.md`**。若同时使用个人目录 `~/.cursor/skills/write-prd/` 与项目内 `.cursor/skills/write-prd/` 两份技能，请自行保持两份 **`references/prd-guide.md`** 内容一致。

### 2. 文件位置与默认命名

- 成品 PRD 必须放在当前项目下的 **`prd/`** 目录中（若目录不存在则创建后再写入）。
- **默认文件名**：使用**项目根目录文件夹名称**（即工作区根路径的 basename），扩展名 **`.md`**。示例：根目录为 `目的地管理` → 默认路径 `prd/目的地管理.md`。
- 若用户**另行指定**路径或文件名，以用户指定为准。

### 3. 已关联远程 Git 时的标题下说明

若当前项目已配置远程仓库（例如 `origin`）：

1. 取得远程地址，并转换为 **HTTPS 可浏览形式**（`https://...`），放在 PRD **需求标题下方**（即 `# 需求标题` 下一段）。
2. 使用 **GitHub Markdown Note** 语法书写，内容遵循下面的模板。
3. 若 `git remote` 仅有 SSH（如 `git@github.com:user/repo.git`），应换算为等价的 `https://github.com/user/repo` 形式；其他托管平台（如 GitLab）同理将 SSH 主机路径换为 HTTPS 仓库根 URL。
4. **若无远程或未配置**：不要编造地址，省略该 Note 块。

模板（有远程时，置于标题下方）：

```markdown
# 需求标题

> [!NOTE]
> **文档仓库**：`https://github.com/org/example-repo`
>
> 上述仓库托管本需求的 Markdown PRD、可交互原型，Markdown 与飞书需求文档同步更新
```

### 4. 扩写时的参考材料（必须）

当任务为**在已有 PRD 上扩充、扩写**时，在动笔写扩写正文之前：

1. **枚举**待扩写原文中出现的**全部**参考链接与引用文档，包括但不限于：「参考链接」「附录」等章节中的 URL、正文中作为设计稿/原型/关联需求/接口说明/技术方案而引用的链接、以及指向仓库内其它 Markdown 或其它格式文档的路径。
2. 对每一项须**实际打开并阅读**（可用浏览器、拉取工具或用户提供的副本）；在已掌握这些材料所承载的约束与背景后，**再开始**扩写正文。
3. 若某链接无法访问（无权限、失效、纯内网），须在交付说明与待确认项中列出，并在扩写中标注依赖缺口；**不得**在未阅读对应材料的情况下臆测其内容或与上游文档「对齐」。

### 5. 原型预览地址加入参考链接章节

若当前的项目有原型（存在 `prototype/` 文件夹，且其中包含 html 文件），且已经通过 `publish-rp` 工具发布并获取到了预览链接，则需要在 PRD 的参考链接章节中加入原型的预览链接。
如果PRD还没有参考或参考链接章节，增加这个章节并补充预览链接。

预览链接的格式通常为：

`http://rp.histar.com/<Git仓库名称>/`

如果不确定预览链接是否存在，可以尝试通过 `curl` 等工具尝试访问上述链接验证。

## 执行顺序（内部）

每次编写或扩充 PRD 时按此顺序执行：

1. 读取并贯彻 **`references/prd-guide.md`**。
2. 解析默认输出路径：`prd/<项目根目录名>.md`（除非用户指定其他路径）。
3. 若存在远程 → 准备 HTTPS 地址与 `[!NOTE]` 块（见上）。
4. **若本次为扩充已有 PRD**：须先完成上文「项目约定」第 4 条（读尽原文全部参考链接与引用文档），未完成不得开始扩写正文。
5. 再进入「工作流分支」与正文起草/扩充。

## 工作流分支

1. **从零起草**：输入以原型链接/截图描述、改动点、目标为主 → 先补全「已知事实」，再按 **`references/prd-guide.md`** 中的文档结构与风格成文。
2. **扩充现有**：用户粘贴或指定仓库中的 PRD 文件 → **先履行「项目约定」第 4 条**（枚举并读完原文中全部参考链接与引用文档）→ 再通读原文、标出缺口（缺场景、缺验收、缺边界等），在原结构上补全，保留用户已有表述，仅增补与理顺。**落盘时**默认仍写入 **`prd/<项目根目录名>.md`**；若用户指定了另一已有文件路径，则以用户路径为准（或按用户要求将扩充结果同步到默认 `prd/` 文件）。

若信息不足，用最少问题补齐：**产品/模块名、目标用户、上线时间或硬约束、是否含数据/埋点、必须对齐的设计稿或接口方**。

## 起草前检查清单（内部执行）

- [ ] 已阅读 **`references/prd-guide.md`**。
- [ ] **扩充任务**：已枚举并阅读**原文中全部**参考链接与引用文档（无法访问的已在待确认/交付说明中列出）；从零起草无此条。

## 起草后检查清单
- [ ] 输出路径为 **`prd/`** 下约定文件名（除非用户另有指定）。
- [ ] 若有 Git 远程，已准备 HTTPS 与标题下方 **`> [!NOTE]`** 说明（无远程则跳过）。
- [ ] 若项目有原型且已经发布，参考链接部分是不是已添加原型的预览链接

## 写作原则

（结构、标题层级与格式以 **`references/prd-guide.md`** 为准；以下为执行时的补充约定。）

1. **可验收**：避免「优化体验」等空话；改为可观察的行为或指标。
2. **与原型对齐**：写明「与原型第 x 屏一致」或「相对原型的变更：…」，避免复述 UI 像素级细节除非对逻辑关键。
3. **改动型需求**：开头用简短「变更摘要」；正文用「现状 / 变更后 / 影响面」写清。
4. **不编造**：缺失的业务规则、权限、金额策略等列入「待确认」并在附录或表格中单列。
5. **语言**：与用户对话语言一致；默认中文正文，专有名词保留英文可接受。

## 从「仅有改动点」时的最小骨架

若输入只有 bullet 列表：先把每条归类到「范围 / 交互 / 数据 / 非功能」；再为每条补「触发条件—系统行为—验收要点」三要素；最后按指南中的章节划分写入对应位置。

## 扩充已有 PRD 时

**前置（须最先完成）**：满足「项目约定」第 4 条——枚举并读完原文中全部参考链接与引用文档后，再执行下列步骤。

1. 保留原标题层级与用户术语，不无故重命名章节。
2. 在缺口处插入小节或表格，用「**【增补】**」前缀标出新增段落（若用户需要无标记版，成稿前再统一删除前缀）。
3. 若原文与新增内容冲突，在指南建议的合适位置增加「修订说明」：冲突点、建议以哪方为准。

## 交付说明

成稿后用几句话说明：文档类型（新写/扩充）、**实际保存路径**、建议评审角色、待确认项列表（若有）。
