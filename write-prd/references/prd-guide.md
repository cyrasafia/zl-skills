# PRD 写作指南

> 海星出游产品团队 PRD 写作规范
> 基于 37 篇 PRD 文档分析总结而成

## 写作原则

### 语言特点

PRD 的语言应具备以下特点：

1. **准确**：一词一义，避免含糊与多重解读。
2. **简洁**：同一信息不重复铺陈，删去赘语。
3. **客观**：只写可核对的事实与规则，不写主观感受；避免「尽量」「大概」等模糊词。
4. **业务视角**：用角色、场景、流程与业务结果说明「要什么」；不以技术栈、实现步骤或架构细节作为叙述主线。
5. **表达一致**：业务概念全文称谓统一；接口、字段等契约信息用表格或指南中的模板呈现，不拆散塞进叙述句。

### 避免长句

**应该尽量避免用过长的句子**，根据场景选择更清晰的表达方式：

- **描述复杂逻辑时**：拆成多个短句，逐一说明
- **描述有多个 case 或分支的场景时**：使用无序列表
- **描述流程或先后发生的事情时**：使用有序列表

**示例：**

❌ 不好的写法（长句）：
```
当用户点击提交按钮时，系统首先校验表单数据是否完整，如果完整则调用后端接口提交数据，如果不完整则高亮显示缺失字段并提示用户补充，提交成功后跳转到列表页，失败则显示错误提示。
```

✅ 好的写法（拆分 + 列表）：
```
用户点击提交按钮时，系统执行以下操作：

1. 校验表单数据完整性
   - 完整：调用后端接口提交数据
   - 不完整：高亮缺失字段，提示用户补充

2. 处理提交结果
   - 成功：跳转到列表页
   - 失败：显示错误提示
```

### 文不如表，表不如图

表述需求时，应该按以下优先级选择表达方式：

1. **图片或流程图**（最优）
   - 状态机图、流程图、系统架构图、时序图等
   - 配合少量辅助文字说明

2. **表格**（次优）
   - 字段定义、状态转换、对比说明等
   - 配合少量辅助文字说明

3. **纯文字**（最后选择）
   - 只有当无法用图片或表格描述时，才使用大量文字

**示例：**

❌ 纯文字描述状态流转：
```
订单创建后状态为待付款，用户付款成功后状态变为已付款，如果用户在付款有效期前未付款则订单取消，已付款的订单在行程结束后变为已完成，如果用户申请退款且退款成功则订单变为已退订...
```

✅ 用状态机图 + 少量文字：
```
（状态机图）

订单状态说明：
- 待付款 → 已付款：用户全额付款
- 待付款 → 已取消：超过付款有效期
- 已付款 → 已完成：行程结束 + 7天
- 已付款 → 已退订：全部退订完成
```

### 避免描述实现细节

PRD 应该描述**想要实现怎样的效果**，而不是**如何实现**。

- ❌ **避免**：描述调用什么接口、使用什么字段匹配、用什么技术方案
- ✅ **应该**：描述功能目标、业务规则、预期效果

**示例：**

❌ 描述实现细节：
```
系统调用用户服务接口 /api/v1/users 获取用户信息，使用 user_id 字段进行匹配，如果匹配成功则返回用户数据，使用 Redis 缓存用户数据...
```

✅ 描述预期效果：
```
系统需要获取并展示用户信息。要求：
- 支持按用户 ID 查询并展示用户基础信息
- 查询不到用户时，显示「未找到用户」提示
- 刷新页面后，已展示的用户信息不丢失
```

> 实现细节属于技术范畴，由开发人员在技术方案中定义。

### 避免写非功能需求

一般需求文档里**不应该**写性能和安全的要求，除非：
- 性能会**显著影响用户体验**（如页面加载超过 3 秒、大量数据处理）
- 有特殊的**安全合规要求**（如涉及敏感数据、金融交易）

**原因：**
- 笼统的「响应时间 < 500ms」「支持 50 并发」对实际开发没有参考意义
- 性能指标应该由技术方案根据实际情况定义
- 常规安全要求（HTTPS、脱敏）是基础设施，不需要在每个 PRD 中重复

**示例：**

❌ 不需要写：
```
## 非功能需求

**性能要求：**
- 响应时间 < 500ms
- 支持 50+ 并发

**安全要求：**
- 敏感信息脱敏展示
- 接口使用 HTTPS 加密
```

✅ 只在必要时写：
```
## 性能要求

此页面需要加载 10 万条历史消息，预计首屏加载时间会超过 5 秒。需要：
- 分页加载，每页 100 条
- 虚拟滚动优化渲染性能
```

### 参考链接应该完整

写作过程中阅读过的相关文档，都应该放在参考链接中，帮助读者快速了解背景和上下文。

**参考链接的要求：**
- 只放**他人能看到的内容**：飞书文档地址、互联网公开网页等
- 不放本地文件路径、内部系统链接等他人无法访问的内容
- **不放本指南本身**：`prd-guide.md` 是 PRD 写作规范，不是需求的上下文背景，不应出现在任何 PRD 的参考链接中

**应该添加的参考链接：**
- 功能迭代时：原先的 PRD（飞书链接）
- 描述局部功能时：整体需求文档、有交互的模块文档（飞书链接）
- 有依赖关系时：依赖系统的文档、接口文档（飞书链接或公开网页）
- 有设计稿时：Figma 链接、原型链接

**示例：**

```
# 参考链接

- 原始需求：定制游行程规划系统 V1.0（飞书链接）
- 关联模块：定制游订单系统（飞书链接）
- 设计稿：[Figma 链接]
- 技术方案：[飞书链接]
```

## PRD 文档结构

### 标准文档结构

```
需求摘要
   - 需求背景：要解决什么问题，或要达成什么目标
   - 大致解决方案：总体思路和核心方案
   （200字以内，不加章节标题）

需求描述
   - 根据实际情况分章节（按页面/模块/流程）
   - 复杂需求可增加概述章节

参考链接（如需要）
   - 设计稿链接（Figma）
   - 原型链接
   - 相关文档链接
```

> **版本信息**：不写在 PRD 里，由项目管理工具（如云效）管理

### 标题层级规范

**飞书和 Markdown 的标题层级不同：**

| 平台 | 文档标题 | 一级章节 | 二级章节 | 三级章节 |
|------|----------|----------|----------|----------|
| 飞书 | 文档标题字段（不写在正文） | # 或 H1 | ## 或 H2 | ### 或 H3 |
| Markdown | # PRD 标题 | ## 一级章节 | ### 二级章节 | #### 三级章节 |

**飞书写法：**
- 文档标题填入「文档标题」字段，正文不需要再写标题
- 一级章节使用 `#` 或 H1
- 二级章节使用 `##` 或 H2

**Markdown 写法：**
- PRD 标题使用 `#`
- 一级章节使用 `##`
- 二级章节使用 `###`

**通用规则：**
- 文档正文（除文档大标题外）一般不超过 3 级标题
- 不使用「一、」「1.1」「2.1」等序号，不利于后续维护
- 只使用标题区分段落，段落之间不需要再加分隔线

**示例（飞书）：**

```
（文档标题：增加线索ID展示）

# 功能需求

## F01: 显示线索ID

## F02: 显示线索入参

# 数据来源
```

**示例（Markdown）：**

```markdown
# 增加线索ID展示

## 功能需求

### F01: 显示线索ID

### F02: 显示线索入参

## 数据来源
```

## 各部分写作要点

### 需求摘要

文档开头直接是一段**需求摘要**（200字以内），包含：

- **需求背景**：要解决什么问题，或要达成什么目标
- **大致的解决方案**：总体思路和核心方案

> 不需要章节标题，直接以自然段落呈现。如果内容简单，一两句话也可以。

#### 写作示例

```
定制师在订单管理中新增出行人时，证件信息依赖手动录入，耗时且易输错。通过后台上传证件照片并 OCR 识别，自动回填字段，降低录入成本与错误率。
```

#### 写作要点

- **简明扼要**：控制在 200 字以内
- **问题导向**：先说问题，再说解决方案
- **目标明确**：清晰说明要达到什么效果
- **用户视角**：从用户或业务的角度描述

### 需求描述

#### 模块划分原则

根据需求实际情况灵活分章，不需要固定的序号结构：

```
## 需求描述

### 涉及页面

### 功能详细说明

### 字段定义（必要时）

### 业务规则

### 交互规则

### 异常处理

### 数据埋点（如需要）

### 国际化要求（如需要）
```

#### 功能描述结构

首先用一段简洁的话描述功能，然后根据实际需求，详细描述功能

功能的详细描述可能包含以下点：

- 功能入口
- 相关页面或窗口的布局
- 功能的操作流程
- 主要字段的计算或取值逻辑
- 状态变化的条件和时机
- 关键节点的判断或校验规则
- 异常情况处理

但是注意，这些只是参考，**并不是所有功能都需要上述所有内容**，应该根据实际情况取舍

如果需要，不在上述范围内的内容也可以写

每一个点尽量以自然段分开，而不要使用子级标题。仅当内容实在太多时，才需要考虑再拆分章节

#### 业务规则写作规范

业务规则应使用列表形式，明确"如果-那么"的关系。

**示例格式：**

```
业务规则

推送有效性判断：推送中至少包含手机号/微信号任一时才算作「有效」

无效：直接过滤（不创建、不更新）

有效：
- type=0（新增）：判断1小时内同一小红书用户ID是否在我方后台已存在有效线索
  - 已经存在：则不自动创建
  - 不存在：自动创建新线索
- type=1/2/3（更新）：按小红书线索ID映射我方线索
  - 命中已存在的线索：仅补全更新字段（不覆盖）
  - 命中未命中已存在的线索：按type=0的新增规则处理
```

**规范要点：**
- 使用列表形式
- 明确条件分支
- 清晰描述每种情况的处理方式
- 使用"-"表示层级

#### 字段说明规范

详细描述每个字段的定义和要求。

**示例格式：**

```
字段：

- 手机号：11位数字，格式验证
- 目的地：文本输入，2-20字符，允许：中文字符、英文字母、数字、空格
- 禁止的特殊字符：' " ; - / * = < > \ . % & | ` $ # ? ! ( ) [ ] { } + ~ ^ @
```

**规范要点：**
- 字段名：清晰标识
- 类型：明确数据类型和长度限制
- 格式要求：明确验证规则
- 禁止内容：列出不允许的特殊字符

#### 交互规则写作规范

交互规则应明确用户操作和系统反馈。

**示例格式：**

```
交互规则

入口：系统右上方展示消息入口和消息个数
```

**交互规则写作要点：**
- 明确触发条件
- 明确操作路径
- 明确页面跳转
- 明确反馈方式

#### 异常处理规范

列出可能的异常场景和处理方式。

**示例格式：**

```
异常处理

- 异常场景 1：[说明] → [处理方式]
- 异常场景 2：[说明] → [处理方式]
```

**异常处理写作要点：**
- 异常场景：描述具体场景
- 处理方式：说明如何处理
- 用户提示：如有，说明提示文案

#### 数据校验规则

**必填校验：**
- 字段为空时的提示文案
- 格式错误的提示文案

**业务校验：**
- 逻辑错误的提示文案
- 边界值的处理方式

#### 图片引用规范

大量使用图片来辅助说明，引用设计稿。

**示例格式：**

```
image.png

流程图说明：
图中展示了从订单创建到支付完成的完整流程
```

**图片使用要点：**
- 文件命名：image.png（按顺序编号，如image2.png）
- 图表说明：简要说明图表内容
- 放置位置：在相关描述之后

## 不同类型文档的写作重点

### 系统设计文档（如OMS、数仓）

**写作重点：**
- 系统整体架构
- 数据结构设计
- 系统关系
- 设计原则
- 技术选型

**特点：**
- 更多使用图表
- 更多使用技术术语
- 相对抽象，偏概念设计

### 功能需求文档（PRD）

**写作重点：**
- 详细的功能描述
- 明确的字段定义
- 清晰的业务规则
- 完整的交互说明
- 异常处理

**特点：**
- 大量使用表格
- 大量使用列表
- 详细的字段说明
- 完整的状态机

### 优化类需求文档

**写作重点：**
- 优化前后对比
- 具体的优化点
- 预期效果

**特点：**
- 简明扼要
- 直接指出问题
- 清晰说明改进点

### 技术接入类文档（如供应商接入）

**写作重点：**
- API对接说明
- 数据格式定义
- 错误码处理
- 接口文档参考

**特点：**
- 大量使用JSON示例
- 详细的数据格式说明
- 明确的对接流程

## 检查清单

提交 PRD 评审前，请确认：

- [ ] 文档开头有需求摘要，能在 200 字以内说明问题和大致解决方案
- [ ] 正文按页面、模块或流程分章，标题层级清晰，正文标题不超过 3 级
- [ ] 表达以业务视角为主，描述「要实现什么效果」，不展开技术实现细节
- [ ] 复杂逻辑已拆成短句、列表、表格或图示，避免大段长句
- [ ] 功能说明覆盖入口、页面/窗口、操作流程、字段逻辑、状态变化等必要内容
- [ ] 字段说明包含定义、类型或格式要求、校验规则和禁止内容（如适用）
- [ ] 业务规则使用列表形式，条件分支和处理方式清晰
- [ ] 交互规则说明触发条件、操作路径、页面跳转和系统反馈
- [ ] 异常处理覆盖主要异常场景，并说明处理方式和提示文案（如有）
- [ ] 如涉及数据埋点，埋点需求已列出
- [ ] 如涉及国际化，国际化要求已说明（语言、币种、时区）
- [ ] 如涉及性能或安全要求，已说明具体业务场景，避免笼统指标
- [ ] 参考链接完整有效，且不包含本地路径或本指南本身

## 常见问题

### Q1：PRD 应该写多详细？

**A：** PRD 的详细程度取决于开发人员的经验和对业务的熟悉程度。一般来说：

- **核心业务逻辑**：需要非常详细，包括所有字段、状态转换、异常处理
- **通用功能**：可以简洁一些，参考已有功能
- **UI 交互细节**：可以略写，参考设计稿
- **接口字段**：必须在 PRD 中明确

### Q2：原型图和 PRD 的关系？

**A：** 原型图和 PRD 是互补的：

- **原型图**：展示界面设计和交互流程
- **PRD**：描述业务逻辑和功能细节
- **建议**：原型图简单交互，PRD 复杂逻辑

### Q3：什么时候更新 PRD？

**A：** 以下情况需要更新 PRD：

- 需求发生变更
- 设计稿更新
- 评审后提出修改意见
- 开发过程中发现遗漏
- 测试后发现逻辑错误

### Q4：如何处理未确定的需求？

**A：** 对于未确定的需求：

- 明确标注：用"待定"、"待确认"标注
- 写出选项：如有多种可能的实现方式，列出所有选项
- 记录讨论过程：写明最终选择的原因
- 注明依赖关系：说明需要等待其他需求明确

## 常用术语

写作中与 PRD 相关的**核心概念、业务流程与系统动作**等约定，便于全文统一引用。

### 核心术语

| 术语 | 英文 | 定义 | 使用场景 |
|------|------|------|----------|
| 订单 | Order | 用户根据行程需求，向平台以特定报价购买一组资源的契约 | 订单管理 |
| 订单详情 | Order Detail | 查看订单完整信息的页面 | 用户操作 |
| 订单变更 | Order Change | 修改订单中行程或增减资源的操作 | 订单管理 |
| 报价单 | Quote | 特定行程用到的资源及其价格清单 | 报价管理 |
| 行程单 | Itinerary | 详细描述特定用户行程的单据 | 行程规划 |
| 资源 | Resource | 用户出游过程中用到的单项有价服务 | 采购、报价 |
| 采购单 | Purchase Order | 对某个单项资源进行采购的单据 | 采购管理 |
| 线索 | Lead | 潜在客户信息 | 销售漏斗、获客 |
| 定制师 | Consultant | 帮助用户规划行程的客服 | 用户沟通、行程规划 |
| POI | Point of Interest | 景点/地点 | 行程规划、资源 |

### 业务流程术语

1. **线索接入** → 用户咨询进入系统
2. **需求沟通** → 定制师与用户沟通需求
3. **行程规划** → 定制师规划行程方案
4. **资源采购** → 采购行程所需资源
5. **报价发送** → 向用户发送报价
6. **成单转化** → 用户确认下单
